三、优势与劣势

✅ 核心优势

  • Monorepo 架构清晰：pnpm + TurboRepo，前后端分离
  • Shipping Provider 模式优秀：接口抽象 + 真实云途价格表接入，可扩展
  • 数据库设计全面：22 张表覆盖完整电商链路，索引优化到位
  • 设计系统成熟：DESIGN.md 681 行详尽规范，色彩/字体/组件体系完整
  • Auth 模块扎实：JWT + bcrypt，密码强度验证，异常处理规范
  • CI/CD 已就绪：GitHub Actions 三阶段流水线
  • 多国架构内置：countries/{id,th,ph} 配置驱动，扩展性好
  • 代码审计意识强：已有 738 行审计报告且持续修复

❌ 核心劣势

  • 零自动化测试：无单测/集成测试/E2E，金融系统不可接受
  • TypeScript 严格模式全关：strictNullChecks: false + noImplicitAny: false
  • 上帝模块反模式：54 个 providers 扁平注册在 AppModule
  • 大量 Mock 实现混入生产代码：8+ 服务返回假数据
  • 前端硬编码严重：大部分屏幕使用 Mock 数据，无真实 API 调用
  • .env 含真实密钥：LLM API Key 明文暴露于代码仓库
  • 无 API 文档：无 Swagger/OpenAPI 规范
  • 内存存储关键数据：Coupon、Region、Holiday 用 Map 存，重启丢失

四、详细发现

🔴 Critical — 严重问题（4 项）

C-01: .env 包含真实云端 LLM API Key CRITICAL

位置: apps/server/.env:25

风险: 真实 API Key 3d929b40e5314221b4... 硬编码在环境变量文件中。虽然 .gitignore 已排除 .env，但该文件存在于本地磁盘，任何有文件系统访问权限的人可读取。若曾被提交到 Git 历史，Token 已永久泄露，攻击者可调用该 API 产生费用或窃取数据。

建议: 立即轮换该 API Key；确认 Git 历史中无泄露（git log --all -p -- .env）；使用 git filter-branch 或 BFG 清理历史；强制所有密钥从环境变量或 Secret Manager 注入。

C-02: JWT Secret 为弱密钥且出现在多个配置源 CRITICAL

位置: apps/server/.env:5 / auth.module.ts:25 / jwt.strategy.ts:11

风险: JWT Secret ace-proxy-super-secret-jwt-key-2026-change-in-production 是弱密钥（纯英文单词组合），抗暴力破解能力低。且 auth.module.ts 和 jwt.strategy.ts 的 fallback 密钥不同（|| 'AceProxySecret2026'），若环境变量未设可能取到不同值导致不可预期的认证失败。

建议: 生成强随机密钥（openssl rand -base64 64）；统一从 ConfigService 单一源读取；移除所有 fallback 硬编码；生产环境强制 JWT_SECRET 必须设置（否则启动失败）。

C-03: 零测试覆盖 — 金融交易系统无自动化安全网 CRITICAL

位置: 全项目 0 个 *.spec.ts / *.test.ts（项目自有代码）

风险: 涉及财务计算、支付回调、账本分账的核心逻辑没有任何自动化测试保护。VaultService 的零和校验、TradeService 的费用计算、AuthService 的密码验证、CouponService 的折扣逻辑——任何修改都可能引入资金计算错误而无人知晓。对于电商金融系统，这是不可接受的技术债务。

建议: ① 立即为 VaultService（零和校验）、TradeService（费用计算）、AuthService（登录注册）编写单元测试
② 为 PaymentController（Xendit Webhook）编写集成测试
③ 目标：核心业务逻辑覆盖率 ≥ 80%，整体 ≥ 60%
④ 配置 Jest + Supertest，加入 CI 流水线

C-04: Docker 安全漏洞 — 数据库端口暴露 + 无健康检查 CRITICAL

位置: docker-compose.yml:11 / apps/server/Dockerfile

风险: PostgreSQL 端口 5432:5432 直接映射到宿主机，若服务器有公网 IP 则数据库对全网开放。Dockerfile 中缺少 prisma generate 步骤（prisma CLI 在 dependencies 而非 devDependencies，但 Client 需要 generate），镜像可能无法启动。

建议: 删除 docker-compose 中的 ports 映射（仅用 Docker 内部网络）；添加 HEALTHCHECK 指令；在 Dockerfile 中添加 RUN npx prisma generate；将 prisma 移入 devDependencies。

🟠 High — 高危问题（12 项）

H-01: 上帝模块 — 54 个 providers 扁平注册在 AppModule HIGH

位置: app.module.ts:114-198

影响: 所有服务互相对所有其他服务可见，无法控制依赖边界。任何一个服务的修改可能隐式影响其他服务。模块无法独立测试、无法按需加载、无法独立部署。启动时一次性创建所有依赖实例，冷启动缓慢。

方案: 按业务领域拆分为独立 NestJS Module：IntelligenceModule、TradeModule（含 Vault + Cart）、ProductModule、HolidayModule、AnalyticsModule、CronModule、CustomerServiceModule、AutoListingModule。每个模块只 exports 其公开服务，imports 其需要的其他模块。

H-02: TypeScript 严格模式全关 — 大量 any 类型绕过编译检查 HIGH

位置: tsconfig.json:15-19

影响: strictNullChecks: false 导致运行时空引用风险（如 TradeService 中 order 为 null 时后续逻辑基于 0 金额计算）。noImplicitAny: false 允许 12+ 处 any 类型参数签名通过编译（createOrder(orderData: any), executeToolCall(toolCall: any) 等）。

方案: 分阶段启用 — Phase 1: 新建文件强制 strict 模式（通过 tsconfig.strict.json + include）；Phase 2: 逐一修复现有文件并逐步扩大 strict 范围；Phase 3: 全项目 strict: true。

H-03: 8+ 服务返回 Mock/假数据 — 生产代码中的"假装工作" HIGH

服务方法问题
HolidayService全部用内存变量模拟，不读写数据库
RegionService全部用内存 Map 模拟，重启丢失
CouponService全部优惠券存内存 Map，重启丢失
IntelligenceServicescrapeAMZ123 / scrapeTikTok返回硬编码数组，无真实爬取
ArbiBotServiceanalyze用 Math.random() 模拟价格分析
VisionQCService全部质检结果全部硬编码
IPFirewallServicecheckLogoLogo 检测返回硬编码值
NotificationService全部 send*只打印日志，实际不发送

方案: 为每个 Mock 服务添加 @todo 标记和运行时警告（this.logger.warn('[MOCK] ...')）；优先实现 CouponService → HolidayService → NotificationService。

H-04: 前端大量硬编码 — 大部分屏幕无真实 API 调用 HIGH

影响: CartScreen 用硬编码 2 个商品，数量增减按钮无事件处理；ProductDetailScreen 永远是同一个 "Premium Silk Abaya"，不接收 productId；PaymentScreen 金额默认值 Rp 2,450,000 硬编码，"上传凭证"只设 state 不上传；Web 管理后台 12 个面板全是假数据。

方案: 优先连接真实 API — 购物车 CRUD → 商品详情 → 支付流程 → 订单管理。Web 管理后台接入 SWR/React Query 调用后端 Dashboard API。

H-05: ChatService 在内存中全量过滤 — N+1 性能风险 HIGH

位置: ChatService.ts:240-249

影响: 先 prisma.aceProduct.findMany() 取全量产品，再在 Node.js 中用 .filter() 做关键词匹配。当产品数量增长至数千条时，每次搜索都全表扫描 + 全量传输到应用层。

方案: 使用 Prisma 的 contains 查询在数据库层过滤；或接入 PostgreSQL 全文索引（tsvector）；或引入 Elasticsearch/MeiliSearch 做搜索引擎。

H-06: PaymentService Mock 模式静默返回假发票 HIGH

位置: PaymentService.ts:30-38

影响: XENDIT_API_KEY 为空时返回 mock 发票数据，用户以为支付已创建但实际没有真实发票。生产环境若配置错误将导致资金流程断裂。

方案: 生产环境 API Key 为空时立即抛出异常（throw new InternalServerErrorException('Payment provider not configured')），而非静默降级为 Mock。

H-07: 导航实现用手动状态切换 — 无 URL 路由 HIGH

位置: apps/mobile/App.js

影响: 使用 useState('LOGIN') + 条件渲染实现页面切换，而非 React Navigation。无法处理深层链接、返回手势、页面转场动画。所有页面共享单一 React 树。

方案: 迁移到 React Navigation（@react-navigation/native + @react-navigation/bottom-tabs + @react-navigation/stack）。

H-08: APIService BASE_URL 硬编码模拟器地址 HIGH

位置: apps/mobile/src/services/APIService.ts:3 — http://10.0.2.2:3000/api/v1

影响: 生产 APK 会指向 Android 模拟器专用地址，真机上无法连接。

方案: 根据 __DEV__ 和环境变量切换；使用 Expo Constants 的 manifest.extra 配置 API 地址。

H-09: 部分 API 端点缺少认证保护 HIGH

影响: /vault/ledger/:orderId（财务写入）、/holiday/update-config（业务配置修改）、/chat/webhook/whatsapp（消息入口）等端点缺少 @UseGuards(JwtAuthGuard)。

方案: 全局应用 JwtAuthGuard（AppModule 中注册为 APP_GUARD），需要公开的端点用 @Public() 装饰器标记。

H-10: TradeController.calculateFees 传入硬编码 totalSpend=0 HIGH

位置: TradeController.ts:43-48

影响: 所有用户始终按最低等级 (EXPLORER) 计算费率，VIP 用户折扣永远不生效——这直接影响营收。

方案: 从数据库查询用户 totalSpend 或通过 JWT payload 传递用户等级。

H-11: RBAC 中间件注册范围不完整 HIGH

位置: app.module.ts:196 — 仅注册 vault, station, holiday 三个路由

影响: payment、order、product 等业务路由不受 RBAC 保护。应该覆盖所有管理端点或全局注册。

方案: 全局注册 RBACMiddleware（.forRoutes('*')），结合 RolesGuard 对特定端点精细化控制。

H-12: 前端 SPA 架构无路由状态管理 HIGH

位置: deploy/index.html (258KB 单文件)

影响: 所有功能打包为单文件 SPA，无代码分割。258KB 首次加载体积大。状态散落在多处 useState 和 sessionStorage 中，无集中状态管理。

方案: 考虑拆分为多页面或引入轻量路由（如 page.js）；引入 Zustand 或 Jotai 做集中状态管理。

🟡 Medium — 中等问题（18 项）

M-01: 多处 throw new Error() 而非 NestJS 异常 MEDIUM

TradeService 用 throw new Error('LEGAL_ERROR: ...') 等原生 Error，客户端收到 500 而非 400 级业务错误码。应使用 ForbiddenException / BadRequestException。

M-02: PaymentService.getInvoiceStatus 无错误处理 MEDIUM

外部 API 调用无 try-catch、不检查 response.ok、不验证 invoiceId 格式（可注入路径）。

M-03: ChatService JSON.parse 无保护 MEDIUM

AI 返回的 arguments 可能是畸形 JSON，JSON.parse 抛出未处理异常导致整个聊天请求崩溃。

M-04: StationService 已废弃方法仍被调用 MEDIUM

setProductStatus 和 updateTrendingProducts 标记 @deprecated 但仍被 SentinelScraper 和 IntelligenceService 调用。

M-05: 缺少 Prisma Migrations 历史 MEDIUM

项目无 prisma/migrations/ 目录，生产环境无法追踪 schema 变更。只能通过 prisma db push 同步。

M-06: 三套 Schema 定义不一致 MEDIUM

ace_proxy_schema.sql、sql-init.sql、Prisma schema 三套数据模型不同步。sql-init.sql 表名完全不同 (users vs ace_users)。

M-07: @types/bcrypt 和 @types/passport-jwt 错误放在 dependencies MEDIUM

类型定义包应在 devDependencies，放在 dependencies 增加生产镜像体积。

M-08: pg 包安装但从未使用 MEDIUM

项目使用 Prisma 作为 ORM，不需要直接使用 pg 驱动。

M-09: NestJS 核心包版本不统一 MEDIUM

@nestjs/common v10 与 @nestjs/config v4、@nestjs/jwt v11、@nestjs/schedule v4 混用。虽然独立包的版本号体系独立，但应统一到最新稳定版。

M-10: Landing 页面通过 JS 注入全局 CSS MEDIUM

Next.js SSR 环境通过 useEffect 创建 style 元素注入动画关键帧，可能导致 hydration mismatch。

M-11: VaultService.recordResaleSettlement 构建条目但不写入数据库 MEDIUM

方法计算了 platformFee/partnerReward/sellerReturn 但 return 后就结束了，未持久化。

M-12: CouponService 全部用内存 Map 存储 MEDIUM

优惠券数据（claimedAt, usedAt, status）存内存，服务重启全部清零。已有 AceCoupon 数据库表未使用。

M-13: 前端使用 sessionStorage 持久化关键数据 MEDIUM

收藏夹、购物车等数据仅存 sessionStorage，关闭标签页即丢失。应迁移到 AsyncStorage（移动端）或后端 API。

M-14: 汇率和运费加价系数硬编码在 ShippingService MEDIUM

汇率（IDR:2200, THB:5.0, PHP:7.8）和运费加价（perKg:40/17/20）硬编码，应移到配置表或数据库，支持动态调整。

M-15: 无 API 文档（Swagger/OpenAPI）MEDIUM

19 个 Controller、60+ 端点无任何自动生成的 API 文档。推荐接入 @nestjs/swagger。

M-16: 无日志系统 MEDIUM

全项目使用 NestJS Logger（console 输出），无结构化日志、无日志聚合、无 ELK/Seq。生产环境排查困难。

M-17: 无性能监控和 APM MEDIUM

无 Sentry/DataDog/OpenTelemetry 集成，无请求耗时追踪。出问题只能看服务器日志。

M-18: ThreatIntelligenceService 硬编码区域列表 MEDIUM

RiskSentryService.ts:17 硬编码 ['JKT', 'LDN']，注释说应从数据库查。新增区域不会被风控监控。

八、总结

AceProxy 是一个 业务设计优秀但工程质量有待提升的项目。核心业务逻辑（Shipping Provider 模式、Vault 零和账本、多国价格体系）体现了扎实的领域建模能力，但 TypeScript 严格模式全关、零测试覆盖、上帝模块反模式等问题构成了显著的技术债务，在支付和财务密集型业务中风险尤其突出。

做得好： Monorepo 架构、Shipping Provider 接口设计、Prisma Schema 完整度、设计系统、代码审计文化、CI/CD 流水线

需要立即改进： 密钥轮换、编写测试、TypeScript 严格模式、模块化重构、API 文档

核心建议： 在上线印尼市场前，至少完成 Phase 1（安全底线）——否则一个 Xendit Webhook 伪造或账本事务失败就可能导致直接资金损失。Phase 2（质量提升）建议在上线后 1 个月内完成，确保系统能支撑规模化增长。
